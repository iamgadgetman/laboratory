# Case study: a BGP session that was up but carried nothing

**Status:** fixed live 2026-10-04 with no session reset and no traffic impact. Making it
permanent in the OPNsense GUI is still pending (step 5).
Addresses are sanitized (`10.40.x` = Fort, `10.20.x` = Hawk, loopbacks
`10.255.0.1/.2`). Prefix-list names in the real config are the network they
match, e.g. `10.40.0.0` = "the Fort /24s".

## 1. Symptom

```
show bgp summary
Neighbor     AS     Up/Down   State/PfxRcd  PfxSnt
10.255.0.1   65551  4d09h24m             0       0
```

The session had been up for days, but sent and received **zero prefixes**.
Nothing was broken from a user's point of view, so it was easy to miss. (As
section 5 shows, neither routing protocol was actually forwarding traffic.)

**Lesson 1:** "Established" only means the TCP session and OPEN exchange
worked. Always check `PfxRcd` / `PfxSnt`, or
`show bgp neighbors X advertised-routes`.

## 2. How BGP filtering stacks

When a neighbor has more than one outbound filter, a route must pass **all** of
them:

```
route ──► prefix-list OUT ──► route-map OUT ──► sent to peer
              (AND)                (AND)
```

Each neighbor had both:
- `prefix-list 10.40.0.0 out`: permits the Fort /24s only
- `route-map Fort out`, which in the *running* config permitted only loopbacks
  and tunnel addresses

No prefix passes both, so the result is an empty set. Inbound had the same shape.

**Lesson 2:** when stacking filters, write down the intersection explicitly.
Two individually sensible filters can combine to block everything.

## 3. Why the route-map didn't match what I'd configured

My first theory was "the policy is designed wrong". Comparing the **saved**
config (`/usr/local/etc/frr/frr.conf`, generated by OPNsense) with the
**running** config (`vtysh -c 'show running-config'`) showed the policy was
designed *right* and was being clobbered:

1. OPNsense's **OSPF page** and **BGP page** each have their own prefix-list and
   route-map tables. I'd used the same names on both (`Fort`, `Hawk`,
   `10.40.0.0` …).
2. FRR has **one global namespace** for prefix-lists and route-maps. The
   generated file therefore defines `route-map Fort permit 10` twice: once from
   OSPF (with seven `match` lines) and once from BGP (with one).
3. A route-map entry holds **one** `match ip address` condition. Each new
   `match ip address prefix-list …` line *replaces* the previous one rather
   than adding to it.
4. Net effect: entry 10 ended up matching only the loopback list. The same
   thing happened to a prefix-list sequence number on the Hawk side:
   `seq 10 permit 10.20.0.0/22 ge 24` was overwritten by
   `seq 10 permit 10.20.0.0/24`, so Hawk could only ever have advertised one of
   its four /24s.

**Lesson 3:** the GUI is not the router. Compare running config with intended
config. The router does exactly what's in the running config, and a generator
can produce something nobody wrote.

**Lesson 4:** in FRR (as in Cisco IOS), several prefix-lists in **one** match
statement are OR'd: `match ip address prefix-list A B C`. Several match
*lines* of the same type don't add up; the last one wins. For OR-logic across
entries, use separate route-map sequence numbers.

## 4. The fix, and why in this order

| Step | Change | Why |
|---|---|---|
| 0 | Back up `config.xml` and `frr.conf` on both boxes | Reversibility |
| 1–2 | `distance bgp 200 200 200` on both sides | eBGP's default admin distance is **20**, OSPF's is **110**. The moment BGP learns the far site's /24s, it would *replace* the OSPF routes in the forwarding table. Raising BGP to 200 first keeps BGP below OSPF. Defensive, as it turned out (see section 5). |
| 3 | Fort: restore `route-map Fort 10 → match 10.40.0.0` and `route-map Hawk 20 → match 10.20.0.0`, then `clear bgp * soft` | Puts back the overwritten BGP entries. A soft clear re-runs policy without resetting the session. |
| 4 | Hawk: the same, plus `prefix-list 10.20.0.0 seq 11 permit 10.20.0.0/22 ge 24` | Restores the clobbered sequence so all four Hawk /24s qualify |
| 5 | Persist in the GUI: give the OSPF-page objects their own names (or delete them, since they only fed inert OSPF filters), and set BGP distance on the BGP page | Runtime `vtysh` changes are lost on the next FRR reload. Without fixing the name collision, the bug comes straight back. |

Distance is applied on **both** sides before **any** policy change, so at no
point can a half-applied change pull traffic onto a new path.

### Result (measured)

```
show bgp summary   (Fort)
Neighbor     AS     Up/Down   State/PfxRcd  PfxSnt
10.255.0.1   65551  4d13h07m             4       4     ← was 0 / 0; session never reset

show ip route 10.20.1.0/24 longer-prefixes   (Fort)
B   10.20.1.0/24 [200/0] via 10.255.0.1 (recursive)    ← new, standby
O   10.20.1.0/24 [110/20] via 10.99.0.1, wg0 onlink
K>* 10.20.1.0/24 [0/0] is directly connected, wg0      ← still the one in use
```

The BGP next hop is the far loopback, resolved *recursively* through the
tunnel. That's the payoff of loopback peering.

The config diff for the whole fix, Fort side:

```diff
 route-map Fort permit 10
- match ip address prefix-list 10.255.0.2
+ match ip address prefix-list 10.40.0.0
 route-map Hawk permit 20
- match ip address prefix-list 10.255.0.1
+ match ip address prefix-list 10.20.0.0
 address-family ipv4 unicast
+  distance bgp 200 200 200
```

**A misleading message along the way.** Both policy commands came back with
`No changes found to be committed!`, and the summary printed straight after
still read `PfxSnt 0`. Neither meant failure: the soft refresh hadn't finished
sending updates. Ten seconds later the counters read 4. **Lesson 6:** verify
with state (`PfxSnt`, `show route-map` hit counts), not with the CLI's
success/failure text, and give the protocol a moment to converge.

## 5. The surprise: neither protocol was forwarding

Right after step 1, `show ip route summary` showed `ospf 6 routes, FIB 0`. The
OSPF routes were in the RIB, but none were installed in the forwarding table:

```
O   10.20.1.0/24 [110/20] via 10.99.0.1, wg0 onlink
K>* 10.20.1.0/24 [0/0] is directly connected, wg0      ← the one in use
```

OPNsense's WireGuard installs a **kernel route for every prefix in the peer's
`AllowedIPs`**. FRR sees those as `K` routes with administrative distance
**0**, which beats every protocol. So the inter-site path has always been
effectively *static*, with OSPF and BGP running alongside as passengers. (There
were also three duplicate kernel entries per prefix, left over from tunnel
restarts.)

**Lesson 5:** `>` (selected) and `*` (installed in the FIB) are the two markers
that matter in `show ip route`. A route without them is learned but not used.

Making dynamic routing actually steer traffic means telling WireGuard not to
install routes (OPNsense: the instance's *Disable routes* option), so FRR
becomes the only route source on `wg0`. That changes the live path to a site
with no physical recovery access, so it's a planned change for a maintenance
window, not part of this fix.

## 6. Things I deliberately didn't do

- **Hand forwarding to OSPF/BGP.** That would move the inter-site forwarding path. The
  Hawk firewall has no physical recovery path, so that change needs its own
  window and an out-of-band way in.
- **Hard-reset the session** (`clear bgp *`). A soft clear re-applies policy
  with zero disruption.
